### 3. ¿Qué relación tiene con las tablas de moneda existentes?

## Relación Conceptual (NO Foreign Key)

Las tablas están relacionadas conceptualmente pero **NO tienen Foreign Keys directas**:

### Tablas de Moneda (Core - Catálogo Estático)

**`moneda`** (`core/models.py`):
- **Propósito:** Catálogo de monedas del sistema
- **Datos:** CLP, PEN, COP, USD, EUR, etc.
- **Características:** Estático, no cambia frecuentemente
- **Campos:** `id_moneda`, `codigo` (CLP, USD, etc.), `nombre`, `decimales`, `vigente`

**`moneda_pais`** (`core/models.py`):
- **Propósito:** Relación entre monedas y países
- **Datos:** Qué moneda se usa en qué país
- **Ejemplo:** CLP se usa en Chile, PEN en Perú, COP en Colombia

### Tablas de Tipos de Cambio (Microservicio - Datos Dinámicos)

**`tipo_cambio_fuente`** (`microservicio/models.py`):
- **Propósito:** Fuentes de APIs para obtener tipos de cambio
- **Datos:** ExchangeRate API, Fixer.io, Banco Central de Chile
- **Características:** Configuración de APIs externas

**`tipo_cambio`** (`microservicio/models.py`):
- **Propósito:** Tasas de cambio históricas obtenidas de APIs
- **Datos:** USD/CLP = 950.50 (fecha: 2024-01-15)
- **Características:** Dinámico, se actualiza diariamente

## Relación Entre las Tablas

### NO hay Foreign Key directa

**`tipo_cambio` NO tiene FK a `moneda`:**

```sql
-- tipo_cambio usa códigos ISO como strings
moneda_origen   CHAR(3) NOT NULL,   -- 'USD', 'EUR', etc.
moneda_destino  CHAR(3) NOT NULL,   -- 'CLP', 'PEN', etc.
```

**Razón:** Los tipos de cambio pueden venir de APIs externas que no conocen nuestras monedas internas. Usar códigos ISO como strings permite:
- Flexibilidad: Puede almacenar cualquier par de monedas
- Independencia: No depende de que la moneda exista en nuestro catálogo
- APIs externas: Las APIs usan códigos ISO estándar (USD, CLP, etc.)

### Relación Indirecta (por código)

**Relación conceptual:**
```
moneda.codigo ('USD') ←→ tipo_cambio.moneda_origen ('USD')
moneda.codigo ('CLP') ←→ tipo_cambio.moneda_destino ('CLP')
```

**Ejemplo:**
- `moneda` tiene: `codigo='USD'`, `nombre='Dólar Estadounidense'`
- `tipo_cambio` tiene: `moneda_origen='USD'`, `moneda_destino='CLP'`, `tasa=950.50`
- La relación es por el código ISO, no por Foreign Key

## ¿Por Qué NO hay Foreign Key?

### Ventajas de NO tener FK:

1. **Flexibilidad:** Puede almacenar tipos de cambio de monedas que no están en nuestro catálogo
2. **APIs Externas:** Las APIs usan códigos ISO estándar, no nuestros IDs internos
3. **Independencia:** El microservicio de tipos de cambio no depende del catálogo de monedas
4. **Histórico:** Puede almacenar tipos de cambio históricos incluso si la moneda se elimina del catálogo

### Desventajas:

1. **Validación:** No hay validación automática de que el código de moneda exista
2. **Integridad:** Puede haber inconsistencias (ej: 'USD' en tipo_cambio pero no en moneda)

### Solución Implementada:

- **Validación en la aplicación:** El código valida que los códigos ISO sean válidos
- **Códigos estándar:** Se usan códigos ISO 4217 estándar (USD, CLP, PEN, COP)
- **Separación de responsabilidades:** 
  - `moneda` = Catálogo interno del sistema
  - `tipo_cambio` = Datos externos de APIs
